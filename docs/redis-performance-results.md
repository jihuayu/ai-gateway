# Redis热路径验收与性能结果

日期：2026-11-07（UTC）。目标 [#23](https://github.com/jihuayu/ai-gateway/issues/23)，任务#24–#27，PR #17。业务候选 `fa94339bd088a7735876b4c7ce1a5230606de5ec`；直接比较基线 `a3884c84e1c07f78ddb9259a1787c19cea88cb5e`。

## 请求边界

默认 `/v1/models` 与 `/v1/chat/completions` 不查询PG、不获取PG连接。鉴权访问Redis，路由使用本机缓存/Redis快照，限流/预算/派发/心跳/元数据/结算使用Redis原子状态及Stream。转发依赖没有PG池和隐式回退。启动、控制台、统计和后台投影仍使用PG。

测试直接禁止前台、后台两个池的query/connect，普通请求、SSE、备用、断流、无效请求和健康检查均完成，调用次数为0。第二实例在PG访问被禁止时从Redis取得新配置并观察供应商禁用和密钥撤销。另用真实TCP代理关闭PG连接并拒绝重连，网关继续响应，恢复后准确补账。

## 同环境前后压测

相同脚本、同环境先后运行两版；每版先执行1次冷请求，再以1/10/50/100并发各执行3轮。真实PG/Redis、本地可控上游；两版Redis实际均为AOF always/noeviction，不拼接旧everysec测量计算降幅。

| 并发 | 基线HTTP P95中位数 | Redis版HTTP P95中位数 | 降幅 |
| --- | ---: | ---: | ---: |
| 1 | 110.88ms | 34.72ms | 68.68% |
| 10 | 404.56ms | 198.97ms | 50.82% |
| 50 | 1225.88ms | 260.92ms | 78.72% |
| 100 | 1518.16ms | 429.89ms | 71.68% |

暖请求路径SQL由22次降至**0次**；候选冷请求与全部12轮的请求SQL均为0，脚本对暖请求非零计数直接失败。后台SQL单独归类，容量检查移至后台并明确标记，避免被旧计数器误标为请求SQL。

两版各484次调用全部200；PG账本各恰好484笔、9680微美元。

100并发候选批次Redis终结完成中位数549.23ms。**整批PG投影核对完成由3558.48ms增加至7805.74ms**：当前后台逐请求事务和多次状态投影形成写入瓶颈，#21应优先优化批量合并与历史增长成本。该时间在HTTP测量结束后主动drain获得，不是生产被动消费延迟认证，不能声称本轮所有阶段都变快。

## 适用范围

Node24.22.1、可见5逻辑CPU、约18.9GB内存，未固定为2vCPU/4GB。总HTTP响应不是纯处理开销，未单独测量SSE块转发；原50ms/20ms目标仍待#22验证。默认Redis有同步持久化、网络和Lua成本，本轮不宣称全RAM或零成本。

PG统计允许滞后，预算展示读Redis实时值。容量10000包含未来终结和unknown更正预留；长期故障或大量未核对费用会停止新准入。Redis身份、预算或日志连续性异常时保守停止，恢复以 [运行手册](operations.md) 为准。
